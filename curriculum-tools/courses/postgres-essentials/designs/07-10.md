## Sol assignment A: lesson 7

Own `curriculum/05-version-check.ts` only. Export VERSION_CHECK and VERSION_CHECK_VISUAL.
Prerequisite row-lock-protects-decision. Fixture pe_edit: id, body, version bigint. Both
sessions read version 1 into psql variables with distinct prefixes. A conditionally updates
body and increments version, B then submits its stale version and affects zero rows. Print
ROW_COUNT immediately so the quiet validator sees 1 versus 0; zero is an application conflict,
not SQLSTATE 40001. B rereads version/body and makes an explicit supplied merge decision
before conditionally saving with the new version. Final body must preserve A's edit and
the reviewed B addition, version 3. Do not teach blindly refreshing only the version token.
No open transaction during human editing. Explain updates still take locks, the convention
requires every writer to advance the token, and zero rows can also mean deletion. Core fits
25 minutes; optional variation: resubmit the stale original token and show it still fails.

## Sol assignment B: lessons 8–9

Own `curriculum/06-write-skew.ts` and `curriculum/07-serializable.ts` only. Export WRITE_SKEW,
WRITE_SKEW_VISUAL and SERIALIZABLE, SERIALIZABLE_VISUAL. Chain prerequisites from lesson 7.
Fixtures pe_on_call_rr and pe_on_call_serial respectively, doctors Alice and Bob initially
on call. Rule: at least one remains. Each decision leaves only if its read counted >1.
Under Repeatable Read, both read 2, update different rows, then commit; final count 0.
Show that a serial schedule would make the second decline. No lost write and no row conflict.
Under Serializable repeat the same schedule: both read 2 and update their own row before
A commits, then B attempts COMMIT. Capture SQLSTATE immediately; expected 40001 and one
surviving doctor. Explain that victim/error location are generally schedule-dependent.
No predicate-lock inventory or unrelated lock fix; this is one controlled comparison.
Use psql VERBOSITY sqlstate for the deliberate error and restore it afterward. Explicitly
rollback as appropriate before final observations. Primary validation must allow exactly
the demonstrated 40001 in lesson 9, rejecting all other errors. Optional variation: finish
A before B starts, so B reads 1, declines and no abort is needed. Supply runnable commands
in the supported challenge field; primary will expose optional variations in the renderer.

## Primary assignment: lesson 10 and integration

Own `curriculum/08-retry.ts`, a supplied bounded standard-library Python/psql client under
`lab/`, module registration, renderer/tests, validator and availability docs. The learner
runs a short shell command; do not require copying or understanding orchestration plumbing.
The client opens real connections in a unique generated scratch schema. Use the same on-call
rule with controlled first-attempt overlap: A commits, B receives 40001; B rolls back and
restarts BEGIN/read/decision/write-if-valid/COMMIT. Fresh read 1 changes B's decision to decline.
Print attempts and SQLSTATE outside the database, query final state from an independent
connection, and clean up all owned sessions/schema in finally. Only 40001 is retryable here;
COMMIT belongs in the try boundary. Bound attempts and statement/client waits. Test no-conflict
success, exhausted attempt budget and nonretryable SQL failure as acceptance cases. No
unknown-outcome replay or external side effects; those belong to lessons 11–12.

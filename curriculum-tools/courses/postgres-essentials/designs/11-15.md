## Primary: lesson 11, supplied client and integration

Own `curriculum/09-unknown-outcome.ts`, `lab/unknown_outcome.py`, shared registration,
renderer/tests, validation controllers, availability docs and acceptance. Export UNKNOWN_OUTCOME and
UNKNOWN_OUTCOME_VISUAL. Prerequisite whole-transaction-retry. A supplied standard-library
Python/psql client runs a bounded application-response withholding experiment on a unique schema.
Submit an increment, commit, withhold the service reply from the simulated caller, close that
request connection, and reconnect to inspect committed state. The caller reports UNKNOWN without
inferring abort. Explicitly name the injection boundary: the service knows the database response;
its caller does not. This is a real committed effect and suppressed application response, not a
PostgreSQL packet-loss or crash experiment. A deliberate unsafe repeat increments twice to expose
the consequence. Optional contrasting mode closes before COMMIT and also gives the caller no
outcome; independent inspection then sees no effect. No automatic replay policy. Bound processes and
waits, validate fresh connection evidence and cleanup on failure.

## Sol A: lesson 12

Own `curriculum/10-request-identity.ts` and a small author evidence/report file only. Export
REQUEST_IDENTITY and REQUEST_IDENTITY_VISUAL. Prerequisite unknown-commit-outcome. Use two SQL
sessions to race the same durable request key. Keep the specified business effect small: one durable
credit-ledger row (key, account, amount, stored receipt); its amount contributes to the account's
credited total. The unique request row IS the effect, so receipt/effect cannot commit separately;
explicitly distinguish this from a separate balance table or remote effect. A inserts key request-12
and holds transaction. B INSERT ON CONFLICT (request_id) DO NOTHING RETURNING ... waits. A commits;
B returns no inserted row, then a separate Read Committed SELECT reconciles the original payload and
receipt. Reconnect A using psql \connect (reuse existing connection parameters), repeat the SAME
request and query stored result, proving one ledger row and one credit. Tie reconnect to lesson 11's
lost response; reconnect here need not fake packet loss. Compare supplied amount/account to stored
payload and explicitly reject reuse with a different payload; do not label every conflict success.
Optional variation A rolls back first and B becomes the sole accepted insert. Include runnable
reset, labelled blocks and cleanup. Explain uniqueness, fresh statement snapshot, payload scope, key
retention and the absence of external exactly-once claims. Real author validation must observe the
wait, core values and variation independently.

## Sol B: lessons 13–15

Own `curriculum/11-blocker.ts`, `12-deadlock.ts`, `13-timeout.ts` and small author evidence/report
files only. Exports BLOCKER/BLOCKER_VISUAL, DEADLOCK/DEADLOCK_VISUAL, TIMEOUT/TIMEOUT_VISUAL. Chain
prerequisites durable-request-identity -> find-the-blocker -> deadlock-cycle.

13: A updates one row and leaves transaction open; B's update waits. From A, inspect B's
wait_event_type/event and pg_blocking_pids joined to the blocking transaction, including state and
xact_start. Identify own sessions with application_name, but use PID edges as actual evidence. A is
active while running its diagnostic; avoid claiming it must appear idle in that query. Commit A,
observe B complete and verify committed final value. No backend cancellation required. Optional
rollback-holder variation changes the surviving value. Avoid assuming PID or exact timing.

14: Two rows; A locks row 1, B locks row 2; B requests row 1 asynchronously, then A requests row 2.
One receives 40P01, its whole attempt fails, survivor proceeds. Capture error SQLSTATE immediately,
explain victim may vary, finish/rollback both and verify exactly one complete attempt survived. Keep
lock/statement timeout guards long enough for detector; avoid requiring global config. Optional
runnable consistent-order comparison causes waiting without a cycle and both succeed. Primary
validator must support either victim and check both SQLSTATEs/final values; never globally allow
arbitrary SQL errors.

15: With A holding a row, B uses BEGIN and SET LOCAL lock_timeout='500ms', statement_timeout='3s';
blocked UPDATE fails 55P03; next SELECT fails 25P02 until ROLLBACK. Separately BEGIN, tentative
write, SET LOCAL statement_timeout='500ms', SELECT pg_sleep(2) fails 57014; next SELECT fails 25P02
and ROLLBACK abandons prior write. Contrast autocommit timeout then successful next SELECT as
optional variation. No savepoint detour. Explain server statement cancellation, an open failed
transaction block, explicit rollback before pool reuse, and that a caller-only deadline or missing
COMMIT response does not prove database abort (lesson 11). Restore all settings and drop fixture.

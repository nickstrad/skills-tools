# Design contract: Essentials 4–6

Keep the fixed PLAN.md identities and first-three teaching voice. Each new file exports one `Module`
and a named diagram string. Parent imports diagrams into the existing renderer and registers modules
in course order. No renderer redesign or additional coaching stages.

## Shared acceptance

Use `01-visibility.ts` as the style/metadata example. Explain unfamiliar SQL/psql syntax in order,
before commands. Include a concrete prediction without requiring typed answers, exact labelled
observations, an application decision and scope limits. Setup must work independently in a clean
database. Drop only the owned pe_* table at the end. Keep 20–30 minutes including setup/cleanup.
Read AUTHORING.md, VALIDATION.md and relevant canonical book digests; optional sources only. Record
exact observed results and any validation limitations in a small per-lesson report under
`validation/`. Do not write progress, edit shared files, build shared lessons.json, or commit.
Authors may validate an extracted one-lesson catalog on their own unique private cluster using the
existing validator design; parent will run the registered exact built lessons independently. Private
clusters must use unique socket paths, no TCP, <=200 MB budget, finally shutdown/removal.

## Lesson 4 — Sol storage author

Own `curriculum/02-reuse.ts` (export `REUSE`, `REUSE_VISUAL`) and `validation/lesson-4-author.md`.
Slug/title are PLAN row 4. Prerequisite `old-reader-retains-history`; one psql session is
sufficient. Delete a bounded table population, VACUUM with truncation explicitly disabled, then
refill with the same shape. Compare pg_relation_size, pgstattuple free/dead counts and row counts
across phases. Prove reuse through increased free space then its consumption without heap growth.
Clarify heap fork versus total/index/TOAST/filesystem accounting; normal vacuum can sometimes
truncate empty tail pages, so this experiment controls that behavior. Do not run VACUUM FULL;
mention its rewrite/locking/capacity tradeoff only in review. Avoid a tuning or FSM-internals
detour.

## Lesson 5 — Sol arithmetic author

Own `curriculum/03-atomic-write.ts` (export `ATOMIC_WRITE`, `ATOMIC_WRITE_VISUAL`) and
`validation/lesson-5-author.md`. Slug/title are PLAN row 5; prerequisite row 4 slug. Two Read
Committed sessions read the same balance, compute supplied replacement values from that stale read,
commit sequentially and lose one intended increment. Reset, then use two
`UPDATE ... SET balance = balance + ...` operations under a deliberately overlapping schedule. Use
`(blocks ...)` session headers supported by the harness and human instructions to switch back to A
while B waits. Observe final arithmetic includes both increments and explain rechecking the updated
row. Short bounded lock/statement timeouts must allow human terminal switching. Keep this about
single-row database arithmetic, not retries, version columns or multi-row rules.

## Lesson 6 — Sol decision author

Own `curriculum/04-row-lock.ts` (export `ROW_LOCK`, `ROW_LOCK_VISUAL`) and
`validation/lesson-6-author.md`. Slug/title are PLAN row 6; prerequisite row 5 slug. Use a tiny
stock/reservation or balance decision where both callers read and decide; show the stale-decision
failure then the same schedule using SELECT FOR UPDATE inside BEGIN/COMMIT. Second locking reader
waits and receives the committed current value, so it re-evaluates and declines an invalid action.
Supply every decision step; a small psql conditional is acceptable only if fully taught and
justified. State that transactions must stay short, ordinary reads still use MVCC, competing writers
participate in locking, and one locked row does not protect arbitrary multi-row invariants. Avoid
lock catalogs (lesson 13), deadlocks, NOWAIT/SKIP LOCKED or retry loops.

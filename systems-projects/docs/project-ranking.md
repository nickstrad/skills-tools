# Systems project ranking for Nick

Added 2026-09-09 at Nick's request. This is the assistant's learning-design judgment, weighted toward
transferable reasoning, unfamiliar failure boundaries, observable local experiments, and worthwhile
use of limited evenings. It accounts for Nick's Go/Kubernetes experience, repeated DDIA reading,
ongoing PostgreSQL study, reported cache/log project exposure and particular interest in object
storage; prior exposure is not treated as mastery. Rank is expected learning value for Nick, not a
required completion order or a claim that every higher-ranked project is easier to start.

The main focus column names the question I would keep returning to throughout that project's course.
Each rationale has two sentences. The original supplied sequence, examples and tiers remain in [the saved project ideas](project-ideas.md)
as source material; this table is the current personalized ranking, not an approved learning agenda.

| Rank | Saved example | Main teaching focus throughout the course | Why I ranked it here |
| --- | --- | --- | --- |
| 1 | Cursor — WAL-first Git storage | **What makes an update authoritative, and when is a replica safe to read?** Separate durable payloads, atomic publication, notifications and replay. | This best connects your object-storage interest and PostgreSQL learning to an unfamiliar architecture whose correctness you can inspect end to end. Publication races, lost notifications and replica rebuilds make several powerful systems ideas work together, provided we keep Git plumbing supplied and defer optional hashing/compaction. |
| 2 | Stripe — Online shard migration | **How can ownership move while writes continue without losing accepted work?** Tie snapshot boundaries, change capture, verification and cutover into a recoverable state machine. | This would push you from understanding individual transactions toward reasoning about correctness across a long-running operation with several failure points. It ranks just below Cursor because the snapshot/change-stream boundary and safe cutover need especially careful scaffolding to fit short lessons, but the reasoning transfers directly to migrations and rebalancing. |
| 3 | Cloudflare — Durable Objects / SQLite ownership | **What makes one owner authoritative, including during handoff?** Study serialization, rejection of obsolete owners and retries after ambiguous replies. | This offers a compact way to examine how ownership simplifies concurrency and exactly where that simplification can fail. For your background, the valuable stretch is a paused old owner returning after reassignment, which forces more precise thinking than a routing function or keyed mutex alone. |
| 4 | RAMP — Fractured reads and atomic visibility | **What consistency guarantee does the application actually need?** Distinguish seeing a transaction's related writes together from serializable execution. | Given your repeated DDIA reading and current PostgreSQL work, this would turn familiar isolation vocabulary into a concrete choice between guarantees. Two small stores can expose the anomaly with little setup, though the repair protocol needs careful teaching so a successful second read is not mistaken for a complete correctness argument. |
| 5 | Pinterest Manas — Kafka as WAL for a derived index | **When is derived state truly disposable?** Make replay, duplicate handling, deletes and checkpoint ordering preserve the same result. | This is one of the clearest ways to turn log-centric architecture into something you can destroy and reconstruct yourself. It ranks below the first four because some log concepts may be familiar, but crash windows between state updates and checkpoints can still provide substantial new depth. |
| 6 | GitHub freno — Replication-lag backpressure | **How should a system regulate incoming work using delayed feedback?** Balance throughput, backlog, reaction time and recovery without oscillating. | This has unusually high learning value per evening because a small controller exposes dynamic behavior that a fixed request limit misses. I would emphasize delayed measurements, overshoot and recovery rather than a simple threshold loop, giving you a useful complement to the storage and consistency projects above it. |
| 7 | Meta LogDevice — Sequencing separate from storage | **Who decides log order, and what remains valid when that authority restarts?** Separate sequence allocation, durable acknowledgements, gaps and recovery. | This could deepen your understanding of the commitments hidden behind a seemingly simple append operation. It ranks below the smaller projects because your reported log-project exposure raises the bar for novelty, and useful sequencer-recovery experiments require more protocol code and careful scope control. |
| 8 | Pinterest — Durable ingestion pipeline | **What has each acknowledgement promised across several durability boundaries?** Trace buffering, retries, offset commits and idempotent external effects. | This makes end-to-end delivery guarantees concrete by crashing between an object upload and the consumer's offset commit. It ranks below the derived-index project because the extra components add setup and overlap, so it earns its place through the external-sink failure boundary and bounded-buffer behavior. |
| 9 | Pinterest — Virtual-shard router | **How does indirection separate data ownership from physical placement?** Follow a shard-map change through routing, stale clients and movement. | This is a strong foundation for reasoning about rebalancing and provides an inspectable use for a small Go component. I rank it here because static hash-to-shard routing may be too familiar by itself; stale maps and ownership changes are the parts that would make it a meaningful step up. |
| 10 | GitHub Spokes — Git replica coordinator | **What does a replica acknowledgement establish, and which copy can safely serve reads?** Relate replication, partial failure, repair and freshness. | This would make replication tradeoffs tangible using Git as an existing storage engine. It ranks below Cursor because it covers fewer new architectural boundaries for you, and we would need to examine coordinator failure and partial publication rather than stop at copying files and counting acknowledgements. |
| 11 | Meta TAO — Graph API over database and cache | **How do access patterns determine the consistency boundary between storage and cache?** Trace invalidation races and the granularity of cached associations. | This is valuable for learning how an application-specific abstraction changes caching and data placement decisions. It ranks lower because a tiny graph API could consume time on familiar application work unless we focus tightly on stale repopulation, concurrent updates and hot adjacency lists. |
| 12 | GitHub — Sharded Valkey rate limiter | **What happens to a global policy when its state is partitioned or stale?** Examine atomic counters, replica lag and membership changes against an explicit limit. | This gives immediate, visible examples of how individually correct counters can fail to enforce the intended system-wide policy. Your Go and cache exposure mean a basic limiter would probably add less than the higher-ranked projects, so the course would concentrate on consistency during failover and resharding. |
| 13 | Discord — Message partitioning and compaction | **How does workload shape interact with physical data layout?** Connect hot partitions, time buckets, read cost and compaction pressure. | This could broaden your storage judgment by making skew and access patterns determine the outcome instead of treating load as uniform. It ranks lower for this project track because ScyllaDB setup and LSM-specific learning can consume the budget, with some of that depth better handled in a dedicated tool course. |
| 14 | GitHub — Relational database partitioning | **Where should a database boundary go, and what coordination cost does it introduce?** Compare workload isolation against lost local joins and transactions. | This is professionally relevant, especially when an operationally simple database has to become several independently managed stores. I rank it lower because the broad example risks becoming a migration-tool walkthrough, while the Stripe and virtual-shard projects isolate its hardest systems questions more sharply. |
| 15 | Pinterest — Memcached / Mcrouter cache routing | **How do membership and placement changes alter backend load?** Connect key movement, cache misses, hot keys and refill storms. | This is a useful compact experiment, but basic hashing and cache-node loss have the greatest overlap with your reported prior cache work. To provide much new growth, it would need to focus on backend amplification and recovery during membership changes, which is narrower than the learning offered higher up. |

**Choosing a first project:** Cursor is my strongest fit if its subject keeps you motivated; start
with durable publication and rebuild, with the remaining mechanisms optional. For a smaller first
project, choose the derived index (rank 5) or lag governor (rank 6), then carry that experience into
one of the top two. A higher rank does not make the lower projects prerequisites.

**Source check for this ranking:** the [Cursor Continuity sections](https://cursor.com/blog/git-at-any-scale#continuity)
support the publication/replay focus; [Cloudflare's SQLite-backed Durable Objects write-up](https://blog.cloudflare.com/sqlite-in-durable-objects/)
supports the per-object ownership/serialization starting point; the [RAMP paper, sections 3–4](https://www.bailis.org/papers/ramp-sigmod2014.pdf)
distinguishes read atomicity and its protocol from serializability. Obsolete-owner injection and the
other teaching choices above are proposed local experiments, not claims that these sources implement
our toy designs. The Stripe link redirected to a page whose article body was unavailable to the
browser, so that row uses the previously supplied synopsis; the remaining rows also rank the saved
local project proposals without claiming a fresh full audit of every company implementation.
